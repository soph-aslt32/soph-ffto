# 推定アルゴリズム

> 状態：統合案（議論中）．ユーザー確認事項が解消するまで実装しない．
> 3つの切り口（積み上げ／状態分解／ロボット中心）の独立設計を，制約に照らして批判・統合したもの．

## ハンドPosの定義難への回答（要点）

ハンドPos には「単独の理論値 c」を定義しない、というのが答えです。ハンドの滞在時間（IN〜OUT）は、ロボットの移動・置く動作・保持したままの待ちを足したものです。また Upper と Lower は腕を共有しているので、ハンド1本の能力は物理的に存在しません。

そこで、理論値はロボット1台に対して定義します。
- ロボットの理論値 W_r^sat は、マテリアル1枚を担当区間すべてに通すのに必要な、待ちを除いた動作時間の合計（秒/枚）です。
- 求め方：ログBの「取った瞬間（搬送元の OUT）」と「置いた瞬間（ハンドの OUT）」を時刻順に並べます。隣り合うイベントの間隔を「区間」とし、区間の型ごとに待ちなしの最短値を求めます。これを入れ替え手順（テンプレート）に沿って足し合わせます。R1 なら 5＋2＋5＋7 ＝ 19 s です。
- この方法は、ログCで待ちがどの動作に入るか、動作内容が欠落しているかの影響を受けません。1周分を足し合わせるので、打刻のずれも打ち消し合います。

ハンドPos の能力（c・稼働率・余裕秒）は、ロボットの値を共有するものとして表示します。ハンド固有の値としては、次の3つを内訳として出します。
- 最短の保持時間（例：R1 Upper は 7 s）
- 実際の保持時間
- 保持中の待ち（何を待っていたか：処理層の完了か、置き先の空きか）

処理層も複数の動作が絡みますが、これは「現在の作業ルールでの最短サイクル c^eff」で扱います。ロボットが処理の完了を待っていたサンプルについて、連続する『置き完了』の間隔を測ります。この値は、待ちの位置に依存しません。純粋な処理時間 s と、ハンドリング（取る・置く・移動）への分け方だけは、ロボットの待機位置に依存します。そのため、s と、事前移動を前提にした理想の値 c^min は参考値とし、ユーザーへの確認事項にしました。

データが足りない値は、推測で埋めません。「上界のみ」「未観測」の印を付けて出します。

## 統合案：ログBの「物理的な受け渡しイベント」を土台にした区間分解と、c^eff / c^min の2層定義

### 0. 基本方針

- 限界はログから計算するだけで求める。合成データの生成器は検証にだけ使う。
- **推定の土台はログCではなくログBに置く。** ログCは、次の3点が実ログで分からないため、主たる根拠にしない。
  - 待ちがどの動作に入るか
  - 動作の粒度
  - 行の欠落
- ログBの OUT は「取られた瞬間」「置かれた瞬間」という物理的なイベントである。これだけで、ロボット・処理層・ハンドの主な量を作る。
- ログCは補助に使う。用途は、MOVE と PICK/PLACE の分割、アイドルと待ちの区別、整合の確認。
- 各推定値には、品質の印を必ず付ける。
  - 「推定」：良いサンプルで得た値
  - 「上界のみ」：良いサンプルが無く、保守側の上限しか出せない
  - 「借用」：他の Pos の値を、ユーザーの許可を得て使った
  - 「未観測」：推定できない。推測では埋めない

### 1. 前処理

1. **構成**（ログX）：Pos の種類、ハンド→(ロボット, Upper/Lower) の対応を取る。マテリアルの経路上で、同じ位置に入れ替わりで現れる非ハンドの Pos 群を「段」とする。
2. **経路**（ログB）：マテリアルごとに IN/OUT を対にし、Pos の列を作る。
3. **ロボットの物理イベント列 E_r**（両ハンドを合わせて、時刻順）
   - PICK 完了：ハンド h に入る直前の Pos（搬送元 P）の OUT 時刻。属性は (m, h, P の段)。
   - PLACE 完了：ハンド h の OUT 時刻。属性は (m, h, 置き先の段)。置き先は m の次の IN の Pos。
   - ラグ：受け渡しの辺ごとに、下流 IN − 上流 OUT の分布を出す（最小・山・幅）。どちらの時刻を物理時刻とみなすかは、確認事項 Q3。
4. **ログCの対応付け**（切り口Cの状態機械）
   - ロボット単位で処理し、1秒内の行は並べ替えを探索する。修復した対には印を付ける。重なり率が 1% を超えたら止めて確認する。
   - ログBのイベントとの照合は「END の一致」ではなく、**区間に含まれるか**（物理イベントの時刻 ∈ [START, END+ε]）で行う。待ちが動作のどこに入っていても成り立つ。
   - 動作内容が記録されている行で、補完の正解率（混同行列）を自己検証する。

### 2. ロボット（＝ハンドPos の定義難への回答の中心）

#### 2.1 区間分解

E_r の隣どうしのイベント対 (e_j → e_{j+1}) を「区間」とする。
- 型 σ：（前のイベントの種別・ハンド・段、後のイベントの種別・ハンド・段）
- 持続：D = t_{j+1} − t_j
- 区間には、正味の動作（MOVE と、取る・置く）と待ちが含まれる。

#### 2.2 区間の正味 g_σ

- 下限側の推定値 d0：件数が絶対数で 5 件以上ある最小の秒の値。割合のしきい値は使わない。低負荷では待ちなしが 0.2% しか無い型があるため。
- 推定は区間で出す：[d0, 2ビン平均]。
- 秒の丸めにより、1 s 未満の待ちは正味と区別できない。この点を明記する。
- 待ちを含まないことが別の根拠で分かる型（例：入れ替え中の PICK_l→PLACE_u）は、点推定にしてよい。

#### 2.3 飽和サイクル W_r^sat

- W_r^sat = Σ_{σ∈テンプレート} g_σ
- テンプレートは、確認済みの入れ替え基本手順（差し替え可能）と戻りの移動から、機械的に作る。
- 例（R1）：[PICK_u@load→PICK_l@proc1] 5 ＋ [PICK_l@proc1→PLACE_u@proc1] 2 ＋ [PLACE_u@proc1→PLACE_l@buffer] 5 ＋ [PLACE_l@buffer→PICK_u@load] 7 ＝ 19 s
- 性質：閉じたサイクルの区間の和は、イベント時刻の一定のずれ（OUT が動作のどの時点で打たれるか、ラグ）が打ち消し合う（隣どうしの差の和なので、途中の時刻が消える）。区間ごとの意味付けを誤っても、和は崩れにくい。
- 照合：全区間が下限側にある「待ちなしサイクル」が観測されれば、その実測の1周と照合する。不一致ならテンプレートの誤りとして警告する。
- 欠けた場合：テンプレートの区間が一つでも「未観測」なら、W^sat は「未観測」とする。上界（観測された最小値の和）は出す。
- ログCの補助：ログCで、MOVE の START〜END が待ちを含まない形と確認できた場合に限り（Q1）、MOVE と PICK のコマンド長から区間を合成してもよい。

#### 2.4 その他のロボットの量

- 現在のパターンでの正味作業：W_r^obs = 窓の中の Σ min(D, g_σ) / 枚数
- 入れ替えの割合 f_ex：ログBだけで判定する（処理層の OUT の時点で、もう一方のハンドが次の材料を保持しているか）。
- 待ち：w = D − g_σ（1 s を超えるもの）。待ち先は、区間の後のイベントの対象の状態で分ける。
  - PICK@P の前の待ち：P が空なら「到着待ち（上流）」、処理中なら「処理待ち（P）」
  - PLACE@Q の前の待ち：Q が埋まっていれば「下流の閉塞（Q）」
  - どちらでもない：「仕事なし」

#### 2.5 ρ と余裕

- 主な値：ρ_r = W_r^sat / T、Δ_r = T − W_r^sat
- 参考：W_r^obs / T、ログCの見かけの稼働率（待ちを含む）、正味の時間率
- ログCの見かけの稼働率は ρ ではないと明記する。

### 3. ハンドPos

ハンドは独立した資源ではない。ハンドが次の材料を取れるのは、ロボットが1周した後に限られる。よって、
- 能力：**c_hand ≡ W_r^sat**、ρ_hand ＝ ρ_r、Δ_hand ＝ Δ_r（共有と注記する）

ハンド固有の値としては、次を出す。
- 最短保持時間 H_min：テンプレート上で、保持している間の正味区間の和。例：R1 Upper は PICK_u@load→PLACE_u@proc1 ＝ 5＋2 ＝ 7 s。
- 実保持時間 H_obs：ログBの IN〜OUT（ラグを補正）
- 保持中の待ち ＝ H_obs − 保持中の正味。待ち先の内訳（処理層の完了待ちか、置き先の空き待ちか）を付ける。下流が律速かどうかを示す。
- ハンドへの MOVE の配分（Σc_h ＝ c_r）は出さない。約束事で、能力と誤読されるため。

### 4. 処理層Pos

#### 4.1 c^eff（主な値）

- 直接サンプル：X = t_PLACE完了@p(k+1) − t_PLACE完了@p(k)。同じ種類のイベントの差なので、打刻のずれは打ち消し合う。
- 良サンプルの条件（A の t_react、B の next-held、C の良サンプルを統合）：
  - (i) PICK@p の直前の区間に待ちがある（D − g ≥ 2 s）
  - (ii) その待ち先が「処理待ち（p）」
  - (iii) 入れ替えが成立している（次の材料を保持済み）
- 条件を満たせば、X ＝ s ＋ 完了から次の置き完了までの正味 ＝ 現在の作業ルールでの最短サイクル。
- 推定値は (p, k) ごとの中央値。待ちの位置やログCの粒度に依存しない。

#### 4.2 s（純粋な処理時間。参考）

- s = (t_PICK完了 − τ_tail) − t_in
- τ_tail は、待ちが明けてから PICK が完了するまでの正味。待機位置で変わる。
  - 層の前で待つ：τ_tail ＝ pick
  - 上流で待つ：τ_tail ＝ move ＋ pick
- ログCで「待ちが明けた時刻」が分かる場合のほかは、Q4 で確認する。c^eff はこの分け方に依存しない。

#### 4.3 c^min（理想の値。参考）

c^min = s + g(PICK) + g(PLACE)。層の前に事前移動している理想の場合。

#### 4.4 良サンプルが無い場合（P9、まれな pid、ロボットが一度も層を待たない場合）

- (i) 打ち切りの上界：滞在時間から作った X の下側分位点を、c^eff の上界（保守側）として「上界のみ」で出す。
- (ii) 同じ段の他の層から借用する。Q6 で許可された場合だけ。
- ロボットの1周が s より長い場合は、ロボットが層を待たないので、良サンプルは原理的に出ない。この場合、律速はロボット側（2.3）にある。

#### 4.5 ρ と余裕

- ρ_p,K = Σ_{m∈W_p,K} c^eff_{p,k(m)} / |W_p,K|
- Δ_p ＝ その層での投入間隔 − c^eff
- 並列層の個々の層の値は参考にとどめる（若い順の振り分けで負荷が偏る）。
- 参考として、ログBの占有率（待ちを含む）も出す。

### 5. コンベアPos

- **ロボット間のコンベア（例：buffer）**：処理層と同じ手順で求める。良サンプルには、下流ロボットが待っていたことと、上流ロボットが次の材料を保持済みであることの両方が必要で、まれになる。その場合は「上界のみ」とし、搬送時間 ＋ 区間の正味で合成した値を、印を付けて出す。
- **先頭段（load）**：取り込み時刻はログAの値（ラグなし）。R1 が到着を待っていた区間（待ち先が上流）から、搬送時間＋τ_tail を求める。
- **自動搬送（feed=auto）・最終段**：下流の IN − ラグの山 − IN の下限側の値を使う。

### 6. 段（並列層をまとめた単位）

- C_S,k = 1 / Σ_{p∈S} (1 / c^eff_{p,k})。参考として C_S^min も出す。前提は「飽和時には全層が使われる」。
- 単層の段で、同じロボットが前後を担う場合は、C ≥ max(c^eff, W_r^sat) とする。
- 処理IDが材料ごとに混ざる場合：C_S(K) = 窓の中の材料の C_S,k(m) の平均（1枚あたりの時間は足し合わせられる）。
- ρ_S,K = C_S(K) / T_K、Δ_S,K = T_K − C_S(K)

### 7. カセット窓

- **c は1か月分をまとめて**、(Pos/段, pid) ごとに推定する。カセットごとに求めるのは、T、ρ、Δ、待ちの内訳、f_ex、飽和の印。c が変わっていないかは、良サンプルの中央値をカセット（または週）ごとの時系列で監視する。
- **窓**：部位 i ごとにずらす。W_{i,K} = [t_i(K の最初の材料), t_i(K+1 の最初の材料))。t_i はその部位に入った時刻。ロボットの区間は、後のイベントの材料に帰属させる（切り口C）。
- **T の求め方**
  - T_K^in：ログAの取り込み間隔の、定常部での中央値
  - T_{i,K}^own：その部位自身の入場間隔の中央値（先頭の q 枚を除く。q は段の層数）
- **Δ の基準**：主な値は T_K^in で計算し、T^own による値も併記する（Q5）。部位が飽和しているカセットでは Δ<0 となり、その部位が能力を超えていることを示す。
- **長い空き**（3 × 中央値の T を超えるもの）：窓から除き、「空き」として別に出す（扱いは Q5）。
- **処理IDが切り替わるカセットの先頭**：過渡状態として「定常部のみ」と「全体」の両方を出す。
- **ボトルネックの推移**：カセットごとに次を出す。
  - b_K^th ＝ argmax_i C_i(K)/T_K、および2位との差
  - b_K^obs ＝ 待ち先の集計で最も多く待たれた部位
  - 飽和の印
  - b^th と b^obs が一致しない場合は、干渉またはモデルの誤りの印を付ける。

### 8. ライン全体

- 処理ID（カセット）ごとに、T_line^min(K) = max_i C_i(K)。i は全ての段、全てのロボット（W^sat）、全てのコンベア。
- 月全体：Σ n_K max_i C_i(K) / Σ n_K。**max を取ってから平均する**。
- ライン全体の余裕：Δ_line,K = T_K^in − T_line^min(K)
- **楽観的な偏りへの対処**（ログからの計算だけで行う）
  1. c^eff を使う。ハンドリングと待機位置による損失を、実測で含める。
  2. 処理IDごとに max を取ってから平均する。
  3. 単層の段とロボットの結合を max で表す（6章）。
  4. 飽和の実測で校正する。飽和したカセットは、部位自身の入場間隔が上流より長い状態が続く、上流の滞在時間が増える、取り込みが待たされる、のいずれかで判定する。そのカセットの実測の限界 T* を予測と比べ、比 κ を出す。**κ は同じ (pid, ボトルネック部位) にだけ適用する。** 飽和したカセットが無ければ「未校正（楽観的な可能性あり）」と明示する。
  5. 拮抗の警告：C の上位2つの比が 0.95 以上で、間の保持枠（コンベア＋ハンド）が2枚以下なら、限界を「下限値」として扱う。
- 出力の意味は「この間隔より短くすると、少なくともこの部位が能力を超える」という**下限**である。実際の限界はこれ以上になる。

### 9. 低負荷データだけの場合に推定できないもの（出力に明示する）

- 待ちなしで観測されない区間の型。W^sat が「未観測」または「上界のみ」になる。合成データの確認では、1か月の低負荷ログで R1 の『buffer に置く→load から取る』の待ちなしは 58 件しかなかった。
- ロボットが一度も完了を待たなかった (p, k)。c^eff は上界のみになる。
- 干渉による損失（κ）。未校正になる。
- 飽和時にだけ現れる動作（退避など）。分からない。
- 低負荷では、入れ替えでないパターンが大半になる。1か月ログの R1 では、PLACE_u@proc1→PICK_l@proc1（置いた後に処理完了を待って取る）が 23639 件、入れ替えは 6066 件だった。このため、W^obs と W^sat は大きく異なる。

### 10. 検証計画

- **真値**
  - T1（要素）：設定値、truth_occupancy、truth_robot_ops（生成器を変更した後は、正味と待ちを分けて出す）
  - T2（合成値）：生成器が設定から計算する truth_capacity.json。c^eff、c^min、C_S、W^sat、テンプレート。
  - T3（ライン限界）：検証専用に、pid を固定して投入間隔を極小にした飽和実行を行い、T_true^min(k) と真のボトルネックを求める。現行の生成器での既知の値は A 52.36 / B 68.99 / C 87.01 s。生成器を変更した後に取り直す。
  - 真の ρ と Δ は、推定と同じ窓の定義で計算する。
- **条件**
  - interval：86.4 / 70 / 62 / 55 / 40 s
  - 処理IDの付け方：per_cassette / per_material
  - logc_missing：0 / 0.5 / 0.9 / 1.0。ログCが無くても、主な量が出ることを確認する。
  - ラグ：0 / 2 / 5 s と、ラグが乗る側
  - 待ちの記録方式 × 待機位置
  - 同じ秒の中の行順の入れ替え
  - 層ごとに違う処理時間
  - ロボット動作のばらつき
  - 低負荷だけの1か月と、低負荷・高負荷が混ざった1か月
- **指標**（目安。合意が必要）
  - g_σ の誤差 ≤ 0.5 s、W^sat の誤差 ≤ 2%、c^eff の誤差 ≤ 1 s
  - ρ の誤差 ≤ 0.02、Δ の誤差 ≤ 1 s
  - カセットごとのボトルネックの一致率
  - T_line^min ÷ T_true（楽観の度合い）
  - 印の正しさ：「上界のみ」とした値が真値以上になっているか、「未観測」の判定が妥当か
- **最重要試験**：86.4 s の1か月ログだけから、A/B/C の限界とボトルネックをどこまで再現できるか。どの値が「上界のみ」「未観測」になるかも確かめる。

## 生成器の修正が必要な点

1. 【必須】ログCで待ちを動作中として記録する方式を追加する。engine._try_robot は現在、op.ready() が偽なら START を出さない。次のように変える：ロボットが手空きになり、予定の先頭が決まった時刻を START にする。条件が整った時刻を物理的な開始、完了を END とする。待ちを入れる位置は、設定（例：log.logc_wait_mode = none / in_next_op_head / in_prev_op_tail / separate_wait_action）で切り替えられるようにする。
2. 【必須】ユーザーの例『マテリアルを持ったまま処理層の完了を待つ』は、現行の生成器では op.ready の待ちではない。dispatch.candidate_tasks が作業を返さない状態（置き先が処理中なので作業の候補が無く、空白になる）に当たる。置き先を先に決めて待つ動作（先に完了する層、または若い順）を予定に入れ、その待ちをログCの動作中として記録できるようにする。手空きで仕事が無いとき（例：置いた後に処理完了を待つ）を空白にするか、動作中にするかも切り替えられるようにする。
3. ロボットの待機位置のルールを追加する：処理層の前へ事前に移動して待つ方式と、現行の『上流で待ち、完了後に移動』の方式を選べるようにする。c^eff と c^min の差（生成器では 3 s/枚）と、s の分け方を検証するため。
4. 真値の拡充：truth_robot_ops に、コマンドの開始・物理的な開始・終了、待ちの理由と待ち先（どの Pos の処理中か、どの Pos が埋まっていたか、到着待ちか、仕事が無いか）、対象のマテリアルを加える。新たに truth_capacity.json を出し、(Pos, pid) ごとの c^eff と c^min、段の C、ロボットの W^sat とテンプレートの区間、待機位置の型を設定から解析的に計算して出力する。取り込みが待たされたかを、取り込みごとに出す。
5. ログBの打刻の選択肢を追加する：OUT・IN を PICK/PLACE の開始と完了のどちらで打つか、ラグを下流の IN と上流の OUT のどちらに乗せるか。
6. ログの並び順の修正：writers.fmt は、打刻した秒の値と、記録に追加した順で並べている。実際の時刻順になっていないので、同じ秒の中で発生順と違う並びになりうる。基本は (秒, 実際の時刻) で並べ、検証用に同じ秒の中の順序を乱すオプションと、START/END の行そのものを欠落させるオプションを追加する。
7. 入力のスケジュールの拡張：カセットごとに投入間隔と pid を指定できるようにする（例：input.interval_schedule）。1か月の中に低負荷と高負荷を混ぜ、ボトルネックの移り変わりと κ の校正を検証するため。
8. 並列層ごとに処理時間を上書きできるようにする。ロボットの動作時間にばらつき（jitter）を付けられるようにする。処理の開始の遅れ（IN から処理開始まで）のオプションを追加する。
9. MOVE を記録するハンドの選択肢を追加する：次の動作のハンド（現行）/ 保持しているハンド / 固定のハンド。
10. 検証専用の補助スクリプト：pid を固定して過負荷で走らせ、T_true^min(k) と真のボトルネックを求める。資源ごとの単離飽和実行（他の段を高速にして、その資源だけを律速にする）も行う。推定側からは使わない。

## ユーザー確認事項

### Q1. 実ログのログCで、ロボットの待ちはどの動作の START〜END に入りますか。また、仕事が無いとき（例：処理層に置いた後、処理の完了を待つだけのとき）は、記録の無い空白になりますか。可能であれば、1〜2サイクル分の行の並び（時刻は相対値、ID は伏せた形でかまいません）を見せていただけますか。

- なぜ重要か：ログCの MOVE・PICK の時間を補助に使えるかどうか、アイドルと待ちを区別できるかが決まります。生成器で再現すべき記録方式も決まります。主な推定はログBで行う設計ですが、低負荷で区間が待ちなしで観測されないときの補完は、この回答に依存します。
- 選択肢：
  - 次の動作の頭側に入る（指令を受けて START → 条件が整うまで待つ → 動く）
  - 前の動作の末尾側に入る
  - WAIT など、待ち専用の動作として記録される
  - 動作の途中に入る（例：移動した後、取る前）
  - 仕事が無いときは空白／仕事が無いときも何かの動作中になる（上のどれかと組み合わせて）
- 推奨：実ログの数サイクル分の並びを見せていただくのが最も確実です。それが難しい場合は、選択肢で回答してください。回答があるまでは、ログCを補助にとどめ、ログBだけで推定する設計で進めます。

### Q2. ログCの動作の粒度と名前の一覧を教えてください。MOVE・PICK・PLACE は別々の行として記録されますか（入れ替えを1動作で記録することはありますか）。MOVE はどちらのハンドの Pos の行に記録されますか。同じロボットの Upper と Lower の START〜END が、時間的に重なることはありますか。

- なぜ重要か：START/END の対応付け（ロボットを1台1資源とし、同時に1動作とする状態機械）と、ログBのイベントとの照合が成り立つ前提です。重なりがあれば、対応付けの方式を作り直す必要があります。
- 選択肢：
  - MOVE・PICK・PLACE が別々の行。重なりなし
  - まとまった単位（1回の搬送、入れ替えなど）で1行
  - 別々の行だが、両ハンドの行が重なることがある
  - その他（ほかの動作名がある、など）
- 推奨：別々の行で重なりなし、という生成器の現仕様に近い形かを確認してください。違う場合は、動作名の一覧と、1サイクル分の例があると助かります。

### Q3. ログBで、搬送元の OUT とハンドの IN、ハンドの OUT と置き先の IN は、それぞれロボットの動作のどの時点（開始時・完了時）で打刻されますか。打刻ラグは、上流の OUT と下流の IN のどちら側に乗りますか。同じ秒の中の行の並びは、発生順として信頼できますか。

- なぜ重要か：統合案では、物理イベントの時刻として『搬送元の OUT』（取った瞬間）と『ハンドの OUT』（置いた瞬間）を使います。1周分の和は打刻のずれに強いですが、処理層の純粋な処理時間と、待ちの判定（2秒のしきい値）は、この仕様の影響を受けます。
- 選択肢：
  - OUT・IN とも動作の完了時。ラグは下流の IN 側（生成器の現仕様）
  - OUT は動作の開始時、IN は完了時
  - ラグは上流の OUT 側にも乗る
  - 分からない（その場合は、ログから山の位置を推定し、複数の仕様で頑健性を確かめます）
- 推奨：分かる範囲で回答してください。不明な場合は、生成器に打刻の選択肢を追加し、どの仕様でも結果が崩れないことを検証で示す方針にします。

### Q4. 処理層の『理論値』に、ロボットの取る・置く動作（と、待機位置から処理層への移動）を含めてよいですか。また、実機のロボットは、次のマテリアルを持ったまま処理層の前へ先に移動して完了を待ちますか。それとも、取った場所で待ち、完了してから移動しますか。

- なぜ重要か：ログから直接測れて、待ちの位置にも依存しないのは c^eff（現在の作業ルールでの最短サイクル ＝ 処理時間＋取る・置く＋必要な移動）です。純粋な処理時間 s と、理想の値 c^min（事前移動を前提）を分けるには、待機位置の情報が必要です。生成器では、この差は 1枚あたり 3 s です。
- 選択肢：
  - c^eff を主な理論値とし、c^min は参考として出す
  - c^min（事前移動を前提にした理想値）を主な理論値とする
  - 純粋な処理時間 s だけを理論値とする（ハンドリングは別に出す）
- 推奨：c^eff を主な値とし、c^min と s は参考値として出すことを推奨します。『あと何秒詰められるか』は、現在の作業ルールで実際に達成できる値で見るのが妥当なためです。待機位置は、分かれば教えてください。

### Q5. 『あと何秒詰められるか』の基準間隔と、時間の扱いについて確認させてください。(1) 基準は、ログAの取り込み間隔（カセット内の定常部の中央値）でよいですか。(2) 外部から指定した取り込み間隔の設定値は、どこかで入手できますか。(3) カセット間の空き時間や、夜間・段取りなどの長い空きは、稼働率の分母から除いて別の項目として出してよいですか。

- なぜ重要か：(1) は Δ と ρ の定義そのものです。(2) は、取り込みが待たされたこと（飽和）の判定に使えます。設定値が無い場合、間隔の最頻値から推定すると、カセット全体が飽和しているときに誤ります。(3) は、月全体の稼働率の見え方を大きく変えます。
- 選択肢：
  - (1) ログAの取り込み間隔を基準とし、部位自身の入場間隔による値も併記する／部位自身の入場間隔を基準にする
  - (2) 設定値が入手できる／入手できない
  - (3) 長い空きは除いて別に出す／含める
- 推奨：(1) ログAの取り込み間隔を基準とし、部位自身の値を併記する。(2) 入手できれば使い、無ければ飽和の判定は装置内の状態（先頭の Pos が埋まっていたか、上流の滞在時間の増加）だけで行う。(3) 長い空きは除いて別に出す。

### Q6. 同じ段の並列層（例：U5-P7/P8/P9）は、同じ処理IDなら処理時間が同じとみなしてよいですか。低負荷でほとんど使われない層や、まれな処理IDのように、良いサンプルが足りない場合は、他の層の値を借りてよいですか。それとも『上界のみ／未観測』として出すべきですか。

- なぜ重要か：若い順の振り分けのため、低負荷では P9 などの良いサンプルがほとんど得られません。借りられるかどうかで、段の理論値 C_S が「推定」になるか「上界のみ」になるかが決まります。
- 選択肢：
  - 同じ仕様とみなし、借用してよい（借用したことを出力に明記する）
  - 層ごとに違いうるので、借用しない（上界のみ・未観測とする）
  - 層ごとの推定値で差を検定し、差が無ければ借用する
- 推奨：層ごとの推定値で差を検定し、差が見られない場合だけ借用し、出力に『借用』と明記することを推奨します。

## 採用しなかった案

| 案 | 理由 |
|---|---|
| ログCの見かけの稼働率（START〜END の合計 ÷ 時間）をロボットの ρ とする | 実ログでは待ちが動作中として記録されるので、ボトルネックの手前のロボットは ρ が 1 近くに見える。能力に対する負荷ではない。参考値としてだけ出す。 |
| PICK/PLACE を『ログCの END ＝ ログBの OUT（±1 s）』の一致、または END とのずれの山で特定する（切り口A・C） | 待ちが動作の末尾に入ると、END は物理的な受け渡し時刻より後になり、照合が崩れる。物理イベントの時刻が区間に含まれるかで照合する方式と、ログBのイベントだけで作る区間分解に置き換える。 |
| コマンドを『末尾の m_k が動作、残りが待ち』に分ける（切り口B）、および t_react ＝ END − e_op とする（切り口A） | 待ちがコマンドの頭側にあるという未確認の仮定で、推測による決め打ちに当たる。c^eff は、この分け方に依存しない直接サンプル（連続する置き完了の間隔）で求める。 |
| δ_resp(ρ) を a·ρ/(1−ρ) などの関数形で回帰し、不動点を解いて保守側の限界とする（切り口C） | 関数形を決め打ちし、低ρ側から外挿している。ログから計算しただけとは言えず、推測が入る。 |
| C_b^eff = (ŝ+h+E[w])/m のように、現在の負荷での待ちを能力に足す（切り口A） | 待ちは負荷によって変わるので、能力の値にはならない。待ちは内訳として別に出す。 |
| 飽和したカセットで学習した補正係数 κ（または α）を、他の pid やボトルネックの種類にも当てはめる | 根拠の無い外挿。κ は同じ (pid, ボトルネック部位) にだけ適用し、それ以外は『未校正』と明示する。 |
| 指定の取り込み間隔を、カセット内の取り込み間隔の最頻値で推定し、入口詰まりの判定に使う（切り口B） | カセット全体が飽和していると、飽和した間隔そのものを指定値と誤認し、判定が自己参照になる。設定値が手に入る場合だけ使い、それ以外は装置内の状態で飽和を判定する。 |
| ロボットの理論値を『観測されたサイクル型のうち最小のもの』とする（切り口C） | 高負荷では維持できない型（たまたま移動が省けた型など）を選ぶ恐れがある。確認済みの入れ替え手順から作ったテンプレートの和を主な値とし、待ちなしの実測の1周は照合に使う。 |
| ハンドへの MOVE の配分（Σc_h ＝ c_r）を、ハンドPos の能力として出す（切り口C） | 配分は約束事で、ルールによって数秒変わり、能力と誤読される。ハンドの能力はロボットの値を共有し、ハンド固有の値は保持時間の内訳だけにする。 |
| 滞在時間分布の左端（下側の分位点）を、純粋な処理時間の点推定とする | 待ちの最小値が 0 にならない (Pos, k) で系統的にずれる（proc1 C で +2.5〜2.9 s）。上界（保守側）としてだけ使う。 |
| 区間・動作の正味時間を、割合のしきい値（件数の2%以上の最小値）と2ビン平均で点推定する | 低負荷では、待ちなしのサンプルが 0.2% しか無い型がある（R1 の buffer に置く→load から取る：29704 件中 58 件）。待ちの分布が 0 付近まで連続していると偏る（真値 5 s に対して 5.47 s）。絶対件数の最小値と2ビン平均の区間で出し、不確かさを明示する。 |
| 待ち時間行列（KLM の拡張）、状態分解（WORK/HANDLE/BLOCK/STARVE）を、ボトルネック判定の主な手段とする（切り口B） | 低負荷では矢印が投入側を指す。また、処理時間の推定と、動作と待ちの分割の両方の誤差が重なる。ボトルネックの予測は max C_i で行い、待ち先の集計は診断と整合の確認にとどめる。 |
| 全部位に共通の時刻窓、またはログAの取り込みを基準にした窓で、カセットごとの ρ を出す | 装置内に仕掛かりがたまる余地があるため、上流が先に進み、ρ>1 が出る（切り口Aの実例）。部位ごとにずらした窓と、マテリアルの帰属で集計する。 |
| 処理IDの構成比で平均した c から max を取る | 楽観的に偏る（61 s に対し、実測は 63.1 s）。カセット（処理ID）ごとに max を取ってから、枚数で重み付けして平均する。 |
